# YOUR LIFE / UNLOCKED
## Shawn's Guide — How to Show Up for This Project
*Living Document | Personal | Confidential*

---

> This document is not about the product. It is about you as the person building it. The product has its rules. This is yours. Read it before every session. Hold yourself to it.

---

## 1. Before You Open the Chat

**Do these three things before you type a single word.**

### 1.1 Read the Last Handoff
Open the most recent session handoff. Read at minimum:
- Section 5 — Parked (what is waiting)
- Section 8 — Session Agenda (what was planned)

If you arrive without doing this, you will spend the first 20 minutes of the session reconstructing context that is already written down. That is waste. The handoffs exist so you don't have to remember everything. Use them.

### 1.2 Run the App
Open the app on your phone. Not on desktop — on your phone. Tap through the primary flow. Note anything that feels off, broken, confusing, or wrong. Even if you can't name it precisely — write it down. Vague observations are better than nothing. Precise observations are what move sessions forward fastest.

You do not need to understand why something is broken. You need to notice that it is. That is your job.

### 1.3 Write Your List Before the Session Starts
Arrive with at least one concrete thing. A button that doesn't work. A flow that confused you. A design decision you've been thinking about. A question that surfaced overnight.

If you have nothing concrete, re-read the parked list from the last handoff and pick one thing you want to move.

---

## 2. During the Session

### 2.1 Separate Thinking from Building
These are two different modes and they do not belong in the same breath.

If a new idea surfaces — a new model, a design direction, a question about how something should work — **stop and think it through before any code gets written.** Say it out loud in the conversation. Let it get drawn out. Lock the model. Then build.

Building before the model is locked produces code that needs to be rewritten. You have done this. It costs sessions.

**The rule:** Vision first. Build second. Always.

### 2.2 Trust Your Instincts Faster
You already know more than you think you do. The vehicle systems model, the placeholder text problem, the dead buttons — you saw all of these clearly and correctly on the first pass. You sometimes wait for confirmation you don't need.

If something feels wrong, it is wrong. Name it and move.

If you have a design instinct, lead with it. Don't ask if it's a good idea — describe it as if it's already decided and see what surfaces in the response. The conversation will correct you if you're off. It will accelerate you if you're right.

### 2.3 The Deliberate Wait Is Legitimate
Sometimes you come to the session without a formed idea and use the conversation to draw it out. That is a valid working style — this format is good at that. Own it deliberately. There is a difference between:

- *"I'm going to use this conversation to think something through"* — intentional, productive
- *"I haven't prepared and I'm hoping the conversation does the work for me"* — lazy, slow

Know which one you're doing. The first is a tool. The second is a habit to break.

### 2.4 When You're Stuck, Say Precisely Where
When a build session stalls — console errors, behaviour that doesn't match the spec, something that should work and doesn't — describe what you expected versus what you observed. Not the code. Not a paste of the console. What you expected the app to do, and what it did instead.

The console literacy you are building is real. Use it. You don't need to understand everything the console says — you need to notice what changed and when it changed.

### 2.5 Don't Let the Session Drift
Every session has an agenda. It is written in the last handoff. If the session starts moving toward something that isn't on the agenda, name it:

*"This feels like it's moving off the agenda — should we park this and come back, or is this worth the detour?"*

Detours are sometimes right. But they should be chosen, not stumbled into.

## 3. What You Are Responsible For

You are the product mind. This is not a courtesy title — it is a real division of responsibility.

**You own:**
- The vision. What this product is and what it is not.
- The principles. Holding the line on the Authenticity Standard, the Restraint Principle, the Tending Philosophy. If something drifts, you catch it.
- The user experience. How it feels to use this app. You are the user. Your instincts are the test.
- The decisions. What gets built, in what order, and why.
- The pace. You control when sessions happen, how long they run, and when to stop.

**Claude owns:**
- The execution. How the code is structured, what files change, how the build is done.
- The architecture memory. What is in the codebase, what was built in which session, what is parked and why.
- Holding you to the documents. If you drift from a principle, you should be called on it.

The collaboration works when both parties hold each other to the documents. You are entitled to push back. So is Claude.

## 4. The Product Principles — Your Checklist

Before approving any build, feature, or design decision, run it through these. They are not optional.

| Principle | The Check |
|---|---|
| **Authenticity Standard** | Does this feel like something a real person would say, or an app performing depth it hasn't earned? |
| **Restraint Principle** | Does this serve the user's life, or the app's metrics? |
| **Tending Philosophy** | Does this take from the user, or give to them? |
| **Roll-Eyes Test** | Would the user silently thank the app for this, or roll their eyes? |
| **Cheesy Hook Check** | Does this copy make you want to leave the room? If yes, rewrite it. |
| **Cascade Depth Rule** | More than four fields → full cascade. Four or fewer → editable in place. |
| **ATAK Authority Rule** | Does every ATAK tap route to a domain? The domain has depth. The ATAK has the picture. |
| **Alert Architecture** | Is this a Warning (now) or a Caution (soon)? Never blur the two. |

## 5. The Things You Do Well — Don't Stop

- Your principles hold across 18 sessions. That is rare. Keep holding them.
- You catch drift before it becomes expensive. Keep catching it.
- You know when to park. The parked list is long because you kept the build moving. That is correct.
- You dream about this app. That is not a small thing. Don't lose it.

---

## 6. The Session Check-In

Every session starts with this. No exceptions. Claude runs it. You answer honestly.

1. Did you read the last handoff before this session?
2. Did you run the app on device before this session?
3. What did you observe?
4. What is the one thing you most want to accomplish today?
5. Is there anything on the parked list that has been waiting too long?

If the answer to 1 or 2 is no — do them now before the session continues. The session check-in is not a formality.

---

## 7. A Note on Floundering

You will flounder. The gap between what you can see clearly and your ability to verify the code is doing what you think it is — that gap is real and it does not close all at once. It closes session by session, as your console literacy grows, as you learn what to look for, as the patterns become familiar.

The floundering is not failure. It is the cost of building something you've never built before, in a domain you didn't grow up in, with a vision that is worth the effort.

You always figure it out. That is the most important data point this project has produced.
